### Process supervision, health check, structured audit logging, and token labeling - 2026-08-19

- **Process supervision**: the server previously ran via a manual `nohup ... & disown` with nothing watching it - if it ever crashed, it just stayed down until someone noticed. New `mcp-server/com.opsgate.mcpserver.plist`, a `launchd` LaunchAgent installed into `~/Library/LaunchAgents/`: starts on login (`RunAtLoad`), restarts on any exit (`KeepAlive`), 10-second `ThrottleInterval` against crash-looping, logs to `~/Library/Logs/opsgate-mcp-server.log` (persistent, unlike `/tmp`). Verified for real: killed the process with `kill -9`, launchd brought it back within seconds, and a real tool call through the live Claude connector worked immediately after.
- **`/health` endpoint**: unauthenticated on purpose (a liveness probe needs to be checkable with no credential, and reveals nothing sensitive) - checks that `tenants/registry.json` actually reads and parses, not just that the process answers HTTP, so "the server is up" and "the server is up but its one piece of persistent state is broken" are distinguishable.
- **Structured per-tool-call audit log**: uvicorn's own access log only ever shows `POST /mcp/claude/ 200 OK` regardless of which `opsgate_*` tool actually ran inside that request - real diagnosis needs the tool name, which only exists one layer up. `replit_tool`/`claude_tool`/`shared_tool` now wrap every registered tool function transparently (zero changes needed inside any individual tool's own body) and append a structured entry - timestamp, tenant_id, tool name, success/failure, duration, error on failure - to `runs/audit.jsonl`. Append-only, no rotation, same reasoning as `decisions.pylog`: an audit trail is supposed to keep growing, not get silently truncated.
- **Token labels**: `opsgate_tenants.issue_token()` now accepts an optional `label` (a non-secret note on what a specific token is *for*, e.g. `"oauth-backing"`, `"replit-connector"`), and a new `list_tokens(tenant_id)` shows every token's label without ever exposing a hash. Exists because of a real near-miss the same day: `OPSGATE_OAUTH_BACKING_TOKEN` had been set to a token that was *also* handed directly to a since-retired Cowork plugin, discovered only when revoking the plugin's token was about to silently break the live OAuth connector too, since they were the exact same string. Minted a fresh, dedicated, labeled token for metco's OAuth backing use and swapped it in - the old token can now be revoked independently without touching OAuth.
- Verified live throughout: the real Claude connector was used to confirm each of the above against the actual running server, not just a local test.
- Regression coverage: `tests/test_opsgate_tenants.py` (5 new checks for labels/`list_tokens`, 28/28 total) and `tests/test_opsgate_mcp_integration.py` (3 new checks - `/health`, a successful call's audit entry, a failing call's audit entry - 51/51 total).
- Drive-by fix: removed a stale `mcp-server/README.md` reference to "the outer project that vendors this engine as a submodule" and "external profile config resolution" - dead since the Phase 5 cutover.
- Full suite: `validate-engine` 0 warnings, `test-all` 58/58, `test_opsgate_tenants.py` 28/28, `test_opsgate_knowledge.py` 228/228, `test_opsgate_oauth.py` 19/19, `test_opsgate_mcp_integration.py` 51/51.

### Split MCP tools into /mcp/replit and /mcp/claude mounts; clean up stale refs - 2026-08-18

- `opsgate_mcp_server.py` now runs two `FastMCP` instances in one process instead of one shared tool list, prompted by clarifying the system's own design: this MCP exists so Claude can compile governed, template-following prompts *for* Replit (Replit is session-based with no memory across prompts, so Claude tracks state externally via `opsgate_init_run` and hands Replit a fresh self-contained prompt each time). Given that, most of the 17 tools are only relevant to one side - `/mcp/replit/` gets 7 (the 5 shared gate/profile/decision tools plus the instruction-sync pair), `/mcp/claude/` gets 15 (those same 5 plus the 10-tool prompt-compiler chain: intake, route, compile, next-phase, parse, lint x2, init x2, export). Explicitly a discoverability split, not a security boundary - both mounts sit behind the same `TokenAuthMiddleware`/tenant resolution.
- Two real implementation bugs found and fixed while building this, both verified against a real booted server before committing: mounting two `FastMCP.streamable_http_app()` instances under one parent `Starlette` app does not cascade the parent's lifespan into the children - each one's `StreamableHTTPSessionManager.run()` had to be entered explicitly via `mcp_x.session_manager` (the SDK exposes it for exactly this case), or every request failed with `RuntimeError: Task group is not initialized`; and the bare mounted path with no trailing slash (`/mcp/replit`) 307-redirects to the trailing-slash form, since each mount's own route registers at `/` - documented and used the trailing-slash URL directly rather than relying on the redirect, since a 307 on a POST is exactly the kind of thing a fragile MCP client might not handle.
- Split `opsgate_sync_instructions` itself into a manifest-only response (`{path, size}`, no content) plus a new `opsgate_sync_file(path)` that fetches one file's content at a time: a real second sync attempt truncated mid-response into invalid JSON at a consistent ~32KB, measured the true combined bundle at ~90KB JSON-encoded, and confirmed via raw authenticated curl that neither this server nor its Tailscale Funnel truncates the response on either leg - the cap is on the calling MCP client, not fixable from this side.
- Same-day stale-reference audit across every tool-serving file: a comment in `opsgate_contracts.py` still referencing the deleted `PROFILES` dict, a `dist/`-bundle justification in `opsgate_knowledge.py`'s `export_ruleset()` docstring, and - after push-back on whether `validate-engine`'s name still made sense ("engine" itself confirmed fine, meaning this system's own logic core, not the retired vendored-distribution sense) - `README.md`'s opening description, its "Using this engine" section, `ENGINE_MANIFEST['purpose']`, and one server comment all still framed this as Replit-only and manual-copy-only, not reflecting Claude's now-equal role or the new sync tools. Renamed `tools/opsgate_setup_lib.py` to `opsgate_tenant_entry.py` - its only remaining content is `build_entry()`, and the old name read as a leftover from the retired `apply-setup.py`/`init-profile.py` era.
- Pre-release, no version bump.

### Tenant-scope run storage and HITL decisions; tighten .env permissions - 2026-08-18

- `opsgate_init_run`/`opsgate_record_decision` were the one part of this system that had never gotten tenant isolation: every tenant wrote into the same flat `runs/` directory and the same global `runs/decisions.pylog`, with no tenant attribution recorded anywhere - inconsistent with the tenant profile/protected-paths system, already properly isolated and tested. Two tenants choosing (or colliding on) the same request id could silently overwrite each other's run, and any caller could append a decision entry for a HITL-ID that looked like it belonged to a different tenant's task with no record of who actually wrote it.
- Fixed: both `*_result` functions now take `tenant_id` (defaulting to `LOCAL_DEV_TENANT_ID`, matching every other tenant-aware function), scoping storage under `runs/<tenant_id>/` and attributing each decision entry with its `tenant_id`. Both CLI commands (`init-run`, `record-decision`) gained the same `--tenant` flag every other tenant-aware command already has. Verified end-to-end against the live server: the same request id under two different tenants now lands in two different `run_dir` paths, and decisions land in a tenant-scoped `decisions.pylog` with correct attribution.
- Also tightened `mcp-server/.env` to 600 (was world-readable 644) - it holds the shared-secret token in plaintext. A local filesystem permission, not git-tracked, so it never shows up in a diff and needs redoing by hand if the file is ever recreated from scratch (a fresh checkout, or a future script that rewrites it) - this exact gap recurred for `tenants/registry.json` later (see the security-hardening work below).
- Pre-release, no version bump.

### Fence caller-supplied prompt text; two more hardening fixes - 2026-08-18

- Prompt-injection mitigation: `outcome`, `must_not_change`, and `acceptance` are free-text fields that can originate from a non-technical user's plain language via `opsgate_intake_request`, with no review before they reach the compiled prompt. `opsgate_prompts.py` now wraps each in a `<<<CALLER_SUPPLIED_DATA>>>...<<<END_CALLER_SUPPLIED_DATA>>>` fence, with a one-time notice near the top of every compiled prompt (both Replit prompts and artifact prompts) stating that fenced content is data describing the task, never an instruction, and does not override scope, gates, or protected paths. Literal delimiter sequences inside caller text are neutralized first, so a field can't fake its own closing marker and have the rest of its content read as if it escaped the fence.
- Explicitly not a complete fix - no prompt-injection mitigation is airtight - but a real structural signal where there was none before; the hard boundaries (protected paths, capability gates) were already enforced by deterministic tool calls regardless of what any prompt text says. Verified against a deliberately adversarial `outcome` field and a delimiter-breakout attempt; added permanent regression coverage in `opsgate_selftest.py`'s `test-all` so this can't silently regress. (A follow-up audit found the fencing pass itself was incomplete - `module`, `known_context.*`, and `scope` paths still reached the compiled prompt unfenced - closed separately; see the security-hardening work below.)
- Two more fixes from the same pass: `resolve_tenant_from_token`'s hash comparison now uses `hmac.compare_digest` instead of `==`, matching the shared-secret check for consistency (not practically exploitable as-is, since comparing hashes rather than raw secrets gives a timing leak no usable signal toward the preimage, but free to make consistent); and `record_decision_result` now rejects `hitl_id`/`answer` over 5000 characters each, bounding how much a single call can grow one tenant's `decisions.pylog` - there was no other size limit on that file.
- Full test suite confirmed green after this and the prior four commits together: `validate-engine.py` 0 warnings, `test-all.py` 57/57, `test_opsgate_tenants.py` 19/19, `test_opsgate_knowledge.py` 219/219, `test_opsgate_mcp_integration.py` 27/27.
- Pre-release, no version bump.

### Full security/correctness audit: close a real gate bypass, tenant-id gaps, path traversal, and harden the rest - 2026-08-18

- A full audit (4 parallel review passes: security, correctness, doc consistency, test coverage) against the real running system, not a self-assessment - found and fixed, worst first: a real capability-gate bypass (a blocked phased run's PHASE-1 was hardcoded to `"planned"` regardless of `route.blocked`, and `opsgate_parse_report` turned a garbage/empty report into a clean "nothing failed" result with no error signal - chained, a blocked/unauthorized task fed any report still produced a real next-phase implementation prompt; `next_phase_prompt_text` now refuses outright when the run state itself is blocked, and refuses to advance on a report with no recognizable content via a new `has_signal` field on `parse_report_result`'s output); `tenant_id` silently dropped in `opsgate_route_request` (the MCP tool), `init_run_result`'s persisted `route.py`, `check_capabilities_result`, and `init_state_result` - all four resolved `local-dev`'s profile regardless of which real tenant was calling, now threaded through like every other tenant-aware function; and a path traversal in `opsgate_knowledge._skill_path()` (built `REPLIT_SKILLS_ROOT/skill/SKILL.md` before checking anything, so an absolute or `../`-laden skill name could read any file literally named `SKILL.md` anywhere on disk - pathlib silently discards the root for an absolute second operand; now allowlist-checked against `list_skill_names()` first, same as its sibling `_instruction_object_path()`).
- Also fixed: the prompt-fencing pass from the prior commit only covered `outcome`/`acceptance`/`must_not_change` - `module`, `known_context.*`, and `scope` paths still reached the compiled prompt unfenced; new `sanitize_inline_text()` flattens these caller-supplied inline fields (a title, a table cell) to one line and neutralizes the fence delimiters, closing the same injection class for fields where a visible fence block would look broken. `opsgate_init_run` had no size cap (a disk-fill vector, unlike the already-capped `record_decision`) - now capped at 50000 JSON-encoded characters. `record_decision_result` accepted any string as `hitl_id` - now validated against `HITL_SCHEMA`'s own id pattern instead of a second, drifting regex. The tenant registry's read-modify-write cycle (`create`/`update`/`delete_profile`, `issue`/`revoke_token`) had no locking - two near-simultaneous writers could race and lose one write; new `_locked_registry()` wraps every mutator in an flock-based critical section, with the lock path following `REGISTRY_PATH` so tests that redirect it into a temp dir are unaffected.
- Lower-severity fixes in the same pass: a registry-corruption error no longer leaks `REGISTRY_PATH`'s absolute filesystem path to a caller; `tenants/registry.json` and its directory were world-readable (644/755) - `_save_registry()` now chmods both to 600/700 on every save, so this self-heals instead of regressing on a fresh checkout or a deleted-and-recreated file; `mcp-server/README.md` had a tool-count arithmetic slip (4+10, forgetting the 5th shared tool) and a stale `decisions.pylog` path description missing its tenant-id segment.
- This same commit also added the five `Unreleased` entries above, documenting the commits since 7.0.0 that had never been written up.
- Every fix has real regression coverage, most verified end-to-end through the actual running MCP server, not just unit-level. Full suite: `validate-engine` 0 warnings, `test-all` 58/58, `test_opsgate_tenants.py` 20/20, `test_opsgate_knowledge.py` 224/224, `test_opsgate_mcp_integration.py` 32/32.

### Add OAuth 2.1 + PKCE support for Claude's org-level custom-connector flow - 2026-08-19

- Claude's real org-level Connectors feature (`claude.ai/customize/connectors`, distinct from a Claude Code plugin's own `.mcp.json`) turned out to be OAuth-only - no field for this server's existing static `X-Opsgate-Token` header at all. That connector path was previously blocked ("contact an organization owner"); the user's IT team granted access to it, making this the real path forward instead of the plugin's bundled connector, which was never able to carry a custom header either and is being dropped.
- New `mcp-server/opsgate_oauth.py`: a minimal OAuth 2.1 + PKCE authorization server, scoped to exactly what this single-operator, single-client deployment needs, not a general-purpose implementation. One static, pre-shared `client_id`/`client_secret` (Claude's connector-setup form asks for exactly a name/URL/client_id/secret, never registers dynamically - Dynamic Client Registration, RFC 7591, is explicitly not required by the MCP Authorization spec). The `/token` endpoint mints nothing new: a successful, PKCE-verified code exchange just hands back one of this server's own existing `X-Opsgate-Token` values (`OPSGATE_OAUTH_BACKING_TOKEN`) as the OAuth `access_token`, so tenant resolution is completely unaffected - a thin authorization-flow wrapper in front of the existing token model.
- `opsgate_mcp_server.py` wires in the new endpoints (metadata discovery, `/authorize`, `/token`) as public, pre-auth routes - a caller has no credential yet when reaching them, that's their whole job. `TokenAuthMiddleware` now also accepts `Authorization: Bearer <token>` alongside the existing header, since that's the transport OAuth 2.1 mandates for access tokens, not optional. A `401` now carries a `WWW-Authenticate` header pointing at this server's own protected-resource metadata, per RFC 9728's discovery convention.
- **Verified live end-to-end, twice, through the actual running server and the real public Tailscale Funnel URL** - once via direct curl (metadata discovery, authorize → token, the issued token authenticating a real tool call), and once via the real Claude connector itself, added through Claude's own "Add connector" UI and confirmed by calling `opsgate_show_profile` through it and getting back real `metco` tenant data. The real request log from that second verification revealed Claude's actual `redirect_uri` (`https://claude.ai/api/mcp/auth_callback`) - `OPSGATE_OAUTH_ALLOWED_REDIRECT_URI` is now pinned to it, closing what was an open-redirect gap while that value was still unknown.
- Regression coverage: `tests/test_opsgate_oauth.py` unit-tests the PKCE/credential-matching logic directly; `tests/test_opsgate_mcp_integration.py` drives the full round trip against the real running server using the real configured `client_id`/`secret`/`backing_token` from `mcp-server/.env` (same reasoning as testing against the real tenant registry elsewhere in that file) - metadata correctness, authorize → token → Bearer-authenticated tool call, and the adversarial cases: a mismatched PKCE verifier, wrong client credentials at both endpoints, a replayed already-redeemed code, and (once pinned) a redirect_uri other than the one pinned.
- Drive-by fix: removed `OPSGATE_PROFILE_CONFIG` from `mcp-server/.env`/`.env.example` - dead since the Phase 5 cutover removed the external-profile-config mechanism it configured; nothing reads it anymore.
- Full suite: `validate-engine` 0 warnings, `test-all` 58/58, `test_opsgate_tenants.py` 20/20, `test_opsgate_knowledge.py` 224/224, `test_opsgate_oauth.py` 19/19, `test_opsgate_mcp_integration.py` 46/46.

## 6.0.8 Deterministic Gates vs. Judgment HITL - 2026-08-10

- Fixed a conflation between deterministic gates and genuine HITL judgment calls, both in `preflight.py`'s output and in `replit.md`'s Mandatory HITL Gate table. `cmd_preflight` internally computes three separately-named, purely deterministic checks (`scope_gate`, `capability_gate`, `protected_path_gate` - each a fixed rule with one correct answer and no judgment involved), but was collapsing all three into a single `required_human_decision` boolean, and the eight-row prose table branded every failing row as a HITL case even though five of the eight rows are deterministic authorization/scope checks, not ambiguity. Only three rows are real HITL cases (owner/path unknown after inspection, two tied valid choices, self-made scope-expanding decision) - the same three cases `replit.md`'s own HITL section already defines.
- `preflight.py` no longer reports `required_human_decision`; it reports `blocked` (honest name for the same deterministic condition) and `blocked_gate_kind: "deterministic"`, since a static pre-execution check can never actually detect real ambiguity - that only surfaces during the work itself.
- `replit.md`'s Mandatory HITL Gate table now labels each row Deterministic or Judgment, and gives each kind its own resolution format: a Deterministic failure returns a new plain "Gate blocked" report naming the exact gate and missing grant (no `DECIDE` reply, nothing to choose between); a Judgment failure still returns the existing "HITL decision required" format with labeled options. `compile-prompt.py`'s MCP-mode gate text and prose-mode gate text were updated the same way, and the `metco_preflight` MCP tool description was corrected to stop calling its result a HITL decision.
- Motivation: every gate should be treated the same way - named, evidenced, and either passed or blocked - with HITL reserved for the narrow case it actually describes. Funneling deterministic authorization gaps through the HITL ceremony overstated how much of the gate surface is really about human judgment, and made every blocked task look like a decision when most blocks just need an explicit grant.
- Verified against the full fixture suite (`validate-kit.py`: 0 warnings after rebuilding distributions, `test-all.py`: 58/58) and against a live compiled MCP-mode prompt, confirming both the Deterministic and Judgment paths render correctly and `lint-prompt.py` still passes.

## 6.0.7 MCP-Aware Compilation and Compiled-Prompt Trimming - 2026-08-10

- Added three opt-in fields to `REQUEST_SCHEMA` and `compile-prompt.py`'s output, all no-ops when absent so every existing request still compiles a byte-identical prompt: `mcp.enabled` swaps the 8-row Mandatory HITL Gate reasoning table for direct tool calls (`metco_check_capability`, `metco_check_paths`, `metco_preflight`, `metco_record_decision`) against a project's own registered MCP server, falling back to the manual table only if a tool call errors or the connection is unreachable; `reference_scope: "minimal"` trims `required_references` down to only the reference docs whose topic keywords actually appear in the request's outcome/module/acceptance/scope text, always keeping `replit.md` and `ai/metco.md`; `known_context` (owners/callers/tests) replaces the open-ended "go discover the owner, callers, and tests" discovery steps with a targeted verify-what's-already-named instruction. Motivation: the compiler had no way to know a target project had exposed METCO's own gate logic as callable MCP tools, so every compiled Replit prompt kept asking the agent to re-derive gate answers in prose and read a fixed reference set regardless of task size — both pure overhead once the same checks are one deterministic tool call away.

## 6.0.6 Per-Action HITL Gate - 2026-07-27

- Added a second, lighter HITL check tier — the Per-Action Gate — distinct from the existing 8-row Mandatory HITL Gate. The Mandatory HITL Gate still runs once before editing, once before each phase, and once before the final report; the Per-Action Gate runs before every individual state-changing action (one edit, one command, one workflow step) and requires an inline `Gate: OK` / `Gate: BLOCKED` statement before acting. Root cause: the Mandatory HITL Gate was only ever being completed once, retroactively, when writing the final report — real evidence from a live run showed a skipped required row, a blank evidence cell, and an ungrounded claim, consistent with the table being backfilled to match a report format rather than actually gating live decisions.
